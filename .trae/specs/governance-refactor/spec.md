# 知识治理专家重构 - 产品需求规格说明书

> 设计原则：以业务价值为锚，以第一性原理拆解知识治理的本质问题，每个模块必须回答「解决什么业务问题、产生什么可度量的价值」。

## Overview
- **Summary**: 将现有知识库项目的前端信息架构从「技术能力导向」重构为「知识治理生命周期导向」，打造 **知识治理专家** —— 一个让 AI 做事、人做决策的知识治理闭环系统。
- **Purpose**: 解决企业知识「散、旧、错、无人管」的根本问题，通过 AI 规模化治理、人裁决把关，持续提升问答准确率与知识健康度。
- **Target Users**: 知识治理专员、知识 Owner、终端问答用户。

## 第一性原理拆解

### 知识治理的本质问题
知识只有被「正确的人」在「正确的时间」以「正确的内容」获取，才产生价值。三个致命失效模式：
1. **找不到**：知识存在但检索不到 → 覆盖率问题
2. **找错了**：召回了过时/错误版本 → 时效性/准确性问题
3. **没人修**：发现问题但无人闭环 → 所有权问题

### 治理闭环（不可拆解的最小闭环）
```
采集（输入质量） → 加工（可检索化） → 应用（分发触达） → 治理（反馈闭环）
     ↑                                                          ↓
     └──────────── 反哺采集（缺口征集/版本换版） ────────────────┘
```
**核心洞察**：治理不是最后一步，而是驱动整个闭环进化的引擎。AI 承担重复判断（预检/分诊/巡检），人承担最终裁决（采纳/驳回/改派），实现规模化且不失控。

### 北极星指标
**问答准确率** = 有引用回答且用户反馈「有帮助」的占比。一切模块都为提升它服务。

## Goals
1. 重组导航为治理闭环 7 模块：智能问答 / 知识采集 / 知识加工 / 知识应用 / 运营看板 / 知识治理 / AI 模型配置。
2. 复用现有后端 API（文档 KB、FAQ、检索、问答、设置、知识中心），将既有能力映射进新框架。
3. 为缺失能力定义后端 API 契约（作为后续产品开发基础），当前阶段用 Mock 数据承载前端演示。
4. 增强问答页：模型切换、深度思考、KB 检索开关、建议词、反馈闭环、无结果→缺口征集。
5. 将 V3 原型 HTML 归档到项目。

## Non-Goals
- 本轮不修改后端 API 契约、数据库结构、Celery 流水线（仅定义契约，不实现）。
- 不接入真实钉钉/Dify 外部系统（跳转链接为配置项，演示用 Mock）。
- 不实现真实 AI 推理逻辑（前端展示 AI 建议项 + 人工裁决交互）。
- 不动 `dify/` 目录源码。
- 不删除现有路由/视图（保留可访问）。

## Background & Context
- 现有项目：RAG MVP（文档 KB、FAQ、混合检索、RAG 问答、设置、用户/APIKey）+ 知识中心（跨库统一视图）。
- 现有导航按技术能力组织：工作台 / 知识库 / 问答库 / 统一检索 / RAG 问答 / 知识中心 / 模型配置。
- V3 原型定义了目标 IA：治理生命周期主线 + AI 执行人裁决模式。
- 后端已有能力可直接复用；新增能力需定义 API 契约并 Mock。

## 模块设计（按业务价值排序）

### M1 · 智能问答（价值交付入口）
- **业务问题**：用户提问能否得到准确、有引用的回答？
- **价值**：直接交付知识价值，准确率是北极星。
- **设计**：问候+输入框、模型切换、深度思考开关、KB 检索开关、建议词、对话气泡带引用与元信息、反馈栏（有帮助/纠错/没找到）、无结果检测→缺口征集。

### M2 · 知识治理（质量控制引擎）
- **业务问题**：问答出错了谁来修？怎么确保修对？
- **价值**：闭环反馈，保障准确率不退化；AI 分诊降人力 80%。
- **设计**：
  - 工单智能分诊：AI 判定根因（缺口/冲突/分段/权限/模型）+ 严重级 + Owner 建议，置信度<0.7 转人工，人裁决（确认/改派）。
  - 质检台账：入库预检留痕，拦截≠删除。
  - 生命周期巡检：有效期到期、90天零引用、Owner调岗、版本冲突，AI 生成建议→人确认推送钉钉待办。
  - 治理标准：命名/元数据/加工路由/健康度权重/注册门禁/权限原则（钉钉文档单一维护入口）。

### M3 · 知识采集（输入质量闸门）
- **业务问题**：垃圾进垃圾出，如何在入库前保证质量？
- **价值**：从源头减少后续治理成本。
- **设计**：
  - 上传前 AI 预检：命名校验、元数据推荐、重复/冲突检测、图片图注起草 → 人裁决（采纳/修改/驳回）→ 放行。
  - 同步源状态：钉钉→Dify 同步健康度。
  - 缺口与征集：聚合无结果问答，AI 判定缺口类型→征集。

### M4 · 知识加工（可检索化）
- **业务问题**：知识入库后能否被准确召回？
- **价值**：提升召回率与引用准确性。
- **设计**：
  - 加工总览：KPI + 流水线（解析→分段→AI增强→打标→索引→回归评测）。
  - 加工引擎配置：按知识类型路由策略（制度→HiQA/手册→父子分段/FAQ→问答对/视频→ASR）。
  - 工具与跳转配置：工具注册表（Dify/同步后台/minerU/OCR/ASR/Rerank/模型网关）含管理入口 URL。

### M5 · 运营看板（可观测性）
- **业务问题**：治理效果如何？哪里需要投入？
- **价值**：数据驱动决策，量化治理 ROI。
- **设计**：KPI（准确率/活跃占比/评测通过率/Owner响应率）+ 健康度分布 + Owner 贡献榜。

### M6 · 知识应用（分发触达）
- **业务问题**：知识通过哪些渠道触达用户？
- **价值**：多端覆盖，最大化知识利用率。
- **设计**：三端卡片（Dify智能体/千问办公/人类门户）+ 问答日志（治理数据源）。

### M7 · AI 模型配置（基础设施）
- **业务问题**：AI 节点用什么模型？成本如何？
- **价值**：统一模型出口，成本可控。
- **设计**：模型接入表 + 节点→模型绑定表（temp/结构化输出/提示词）+ 用量成本表。

## 后端 API 契约定义（后续实现基础）

以下为本轮前端 Mock、后续需后端实现的 API 契约：

```
# 工具注册表
GET    /api/v1/tools                    # 工具列表
POST   /api/v1/tools                    # 注册工具
PUT    /api/v1/tools/{id}               # 更新工具

# 知识治理
GET    /api/v1/governance/tickets       # 工单列表（AI分诊后待人裁决）
POST   /api/v1/governance/tickets/{id}/adjudicate  # 人裁决
GET    /api/v1/governance/quality-ledger            # 质检台账
GET    /api/v1/governance/lifecycle                 # 生命周期巡检结果

# 知识采集
POST   /api/v1/collection/pre-check    # 上传前AI预检
GET    /api/v1/collection/sync-sources  # 同步源状态
GET    /api/v1/collection/gaps          # 缺口看板

# 运营
GET    /api/v1/operations/health        # 知识健康度
GET    /api/v1/operations/owner-stats   # Owner贡献

# 应用
GET    /api/v1/apply/logs               # 问答日志

# 模型
GET    /api/v1/models                   # 模型接入列表
GET    /api/v1/models/bindings          # 节点模型绑定
```

## Functional Requirements

### FR-1：导航重组为治理闭环 7 模块
导航：智能问答 / 知识采集 / 知识加工 / 知识应用 / 运营看板 / 知识治理 / AI 模型配置，分「功能区」「平台配置」两组。顶栏：连接状态、北极星指标、反馈→治理脉冲条。

### FR-2：智能问答增强
模型切换、深度思考、KB 检索开关、建议词、对话带引用与元信息、反馈栏、无结果检测。

### FR-3：知识采集 AI 预检闭环
上传→预检报告（4项）→人裁决→放行。同步源状态表。缺口征集表。

### FR-4：知识加工总览+工具注册表
KPI+流水线、策略路由表、工具注册表（含管理入口 URL）。

### FR-5：知识应用三端+问答日志
Dify/千问办公/人类门户卡片 + 问答日志表。

### FR-6：运营看板 KPI+健康度
4 KPI + 健康度分布表 + Owner 贡献榜。

### FR-7：知识治理工单分诊
AI 分诊表（确认/改派交互）+ 质检台账 + 生命周期巡检 + 治理标准。

### FR-8：AI 模型配置
模型接入表 + 节点绑定表 + 用量表 + 提示词查看。

### FR-9：V3 原型归档
`docs/知识问答智能体原型V3.html` 存在。

## Non-Functional Requirements
- **NFR-1**: `pnpm type-check` 通过。
- **NFR-2**: 现有路由仍可正常访问。
- **NFR-3**: 复用 Element Plus + PageContainer，不引入新 UI 库。
- **NFR-4**: 中文界面，与现有设计语言一致。

## Constraints
- **Technical**: Vue 3 + TS + Element Plus + Pinia + Vue Router；后端 API 本轮不变。
- **Business**: AI 只建议，人裁决；治理台账源在钉钉，页面只读。
- **Dependencies**: 现有 `web/src/api/*`、`web/src/types/*`、`web/src/components/*`。

## Assumptions
- 现有后端 API 可正常工作。
- 新增能力用 Mock 数据，后续按 API 契约对接后端。
- 用户接受部分模块为演示态。
