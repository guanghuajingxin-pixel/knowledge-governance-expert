# 企业知识问答增强与验收

本次将 `/api/v1/search/chat` 和 `/api/v1/search/chat/stream` 统一到 `enterprise.py` 的证据问答链路。目标是企业真实问题的端到端正确率超过 90%，当前尚未完成企业专家题集验收，不能把代码测试或单题成功当作准确率结论。

## 主链路

1. 对当前会话做指代消解，明确对象、范围和必答要点，最多拆成三个检索查询。没有必要对象时澄清。
2. 对所选 Dify 数据集同时执行语义与全文检索；所选本地知识库执行混合召回和重排。按 RRF 排名融合，按完整内容和来源去重，限制单文档数量及上下文总长度。RRF 分数不作为正确概率。
3. 模型逐项判断资料是否相关、覆盖问题、存在版本冲突。检查异常视为证据不足。
4. 不足时复用现有加工表的标签、关键词、摘要和双向文档关系来发现候选标题，再检索原文。最多补查一次，受 `planning_enabled` 和 `max_retrieval_rounds` 控制。
5. 仍不足时调用 `dws aisearch enterprise --types document`，按明确文档名与子问题分别检索，最多三路，保留各路片段。包括零命中、主题错配、部分覆盖、上游检索失败，不只判断向量库是否返回结果。
6. 在线 `adoc` 可以进一步调用 `dws doc +fetch`（单轮最多两次原文读取）。办公文件仅使用实际返回的正文检索片段；不可读编码表格被明确标注，不能用来证明审批角色或金额。所有搜索片段均保留 partial 标记。
7. 生成结构化事实，每条关联原文 ID 和摘录。服务端校验 ID、摘录存在性（只忽略空白与 Markdown 显示标记），再由独立模型调用检查原文是否支持该事实及条件、例外、数值、版本。
8. 未通过可修正一次；仍未通过不发布草稿。通过后由服务端生成引用编号，保证答案编号与引用卡片一一对应。

`answered` 为已核验完整回答；`partial` 为已核验的部分信息；`insufficient` 为证据不足；另有 `clarification` 和 `greeting`。自动核验仍可能误判，必须接受业务专家评测。

前端展示证据状态、钉钉补查情况、来源异常和可展开的原文依据。状态、原文、引用编号随会话保存，恢复历史时不丢失。流式推送检索进度并每 15 秒保活，事实文本通过核验后才下发。单轮总时限 300 秒，用户停止或断开会取消任务和 DWS 子进程。

## 接入与权限

- 使用系统里已经保存的问答模型和 Dify 配置，凭据按请求传递，不再为问答修改全局 settings 对象。
- `dify_dataset_ids=null` 使用系统配置的默认数据集；`[]` 明确跳过 Dify。没有默认数据集且未选择数据集时仍可尝试 DWS。
- 普通用户只能请求系统向企业问答开放的默认 Dify 数据集；管理员可选择其 Dify 服务凭据能访问的数据集。这里沿用系统级 Dify 共享知识权限，并未实现 Dify 文档级用户 ACL。敏感私有知识不得放入所有员工共享的默认集合。
- 本地知识库按所有者/管理员检查，并过滤数据库已删除的文档，避免 ES 清理滞后造成误引用。
- DWS 查找可执行文件的顺序为 `DWS_BIN`、服务进程的 PATH。建议为服务设置绝对路径；新版 CLI 的 `aisearch enterprise`、`profile list`、`doc +fetch` 需可用。
- 超级管理员可使用 CLI 的明确当前组织账号；普通用户与普通管理员必须配置 `QA_DWS_USER_PROFILES`，格式为 JSON 对象：`{"平台用户UUID":"corpId:userId"}`。值应来自 `dws profile list --format json` 的真实 profile，并对应获准使用的身份。读取和搜索固定使用同一身份，不改变全局当前组织，也不自动跨组织搜索。
- 未绑定、未登录、权限错误、格式错误和超时都在质量提示中保留，不能伪装成“知识库里不存在”。DWS 凭据由 CLI 管理，程序不读取或记录 token。
- 本版本没有引入新的数据库表；摘要/图谱导航依赖已有知识加工迁移，原文链接回填依赖已有钉钉映射表。缺少这些可选表时导航降级并提示，基础检索继续运行。

## 摘要、打标、图谱与记忆

复用已有 `ProcessedDocument` 和 `KnowledgeRelation`，避免重复加工企业全库。建议治理人员优先补齐高频问题涉及的制度：标题/编码、责任部门、适用公司、业务域、版本、生效时间、废止状态、原始链接和同义词。当前模型生成的摘要与文档关系仅用于查找线索；即便关系类型叫“因果”，也不把它当作确定的业务因果事实。

对于数字、审批矩阵、例外条件，优先改善入库解析，保留表头、单位、跨页表格和层级章节；不能靠模型总结修复缺失的原文。扫描件和图中流程需要 OCR/版面解析并由 Owner 抽检。未来若增加版本/有效期结构化字段，应先补历史数据和业务审核，再作为检索硬过滤条件。

记忆按用户持有的会话从数据库恢复最近八条消息，仅用于指代消解。历史助手回答、纠错反馈不直接晋升为企业事实，partial/insufficient 不写入 `last_answer` 事实上下文。关闭 `long_memory_enabled` 会禁用会话上下文。跨会话的个人偏好、经 Owner 审核的 FAQ 以及失效时间可后续单独建模；当前没有把聊天记录累积成全局共享知识。

新主链路使用程序化的检索/补查/核验步骤，保留旧 DeerFlow 代码但不再由问答 HTTP 入口自动路由。旧侧车的自主子智能体、自由探索、限时继续提示、全局长期记忆和文件工具不属于新主链路；相应旧配置不会绕过证据检查。深度思考增加召回范围，事实生成温度固定为 0。

配置页已同步这些实际行为，旧版人格/技能编辑入口标为兼容设置。Top-K 默认取保存配置，API 可逐次覆盖；深度思考至少取 12。企业知识检索轮数限制为 1–2，单次结构化生成/核验的 token 上限至少 3000。澄清关闭后，对象不明确的问题返回证据不足，不猜测对象。智能模式允许问候直接应答，强制模式仍执行检索。问答页按顺序加载模型配置，避免并发加载导致模型选项随机被覆盖。

供应商兼容使用 JSON 文本加 Pydantic 校验，不要求供应商支持强制工具选择或 JSON Schema response_format。DeepSeek 的问题规划阶段按其[官方思考模式参数](https://api-docs.deepseek.com/guides/thinking_mode/)关闭额外思考，以控制延迟；证据审核仍保留独立调用。

## 90% 验收方法

至少收集 100 道独立真实问题，建议包含流程/角色、数值/条件、跨文档对比、别名/简称、多轮指代、版本冲突、知识缺口、DWS 独有知识和越权请求。每道题记录业务专家标准答案、必要原文 ID、适用范围与时效。调参集与最终验收集应隔离；不要把验收题改写成训练 FAQ 后又以同题验收。

`corpus.example.jsonl` 仅是两行格式模板，不含虚构企业标准答案。将其复制到本地私有题集并替换占位内容。`dify_dataset_ids: []` 表示 DWS 专项题；常规题应填真实数据集 ID 或省略该字段使用默认配置。题集与评测输出可能包含企业资料，不应提交到公共仓库。

从仓库根目录运行（使用环境变量提供测试用户已有的 JWT/API Key，不要将 token 放进命令参数）：

```bash
services/kb-api/.venv/bin/python scripts/evaluate_qa.py /path/to/private-corpus.jsonl --output /path/to/new-evaluation
```

`QA_EVAL_TOKEN` 必须在运行环境中设置。默认调用本地 8000 端口的 `/api/v1/search/chat`，可用 `--endpoint` 指定测试环境。每题保存原始响应、耗时和证据快照；`review-template.jsonl` 提供待专家判分模板。

专家核对原文后填入 `correct`、`reviewer`、`reason`，保留对应的 `answer_hash`。再次离线评分：

```bash
services/kb-api/.venv/bin/python scripts/evaluate_qa.py /path/to/private-corpus.jsonl --responses /path/to/new-evaluation/responses.jsonl --annotations /path/to/reviewed.jsonl --output /path/to/final-report
```

只有题数至少 100、所有题都完成专家审核、端到端正确率严格超过 0.90 才 `accepted=true`，脚本退出 0；未达标退出 2。部分回答、失败、超时、该答却拒答都保留在分母；正确拒答仅限专家预先标记不可回答的题目。修改回答或引用快照会使旧审核失效。自动关键词和来源命中检查单独列为辅助指标，不能代替专家准确率。

当前验收只判断这套题集上的结果，不声称统计意义上真实生产准确率下界超过 90%。应持续将真实纠错问题加入新的回归集，并按部门、问题类型、模型版本监测准确率、拒答率及 P95 耗时。
